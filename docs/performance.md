# Performance

**English** · [简体中文](performance.zh-CN.md)

All numbers here were measured on the machine below with the commands shown. If a
number is not here, it was not measured; nothing in this file is projected.

> **Version note (2026-11-24):** these timings were measured on the published
> 0.7.0 `win-x64` binary (`AirGlance.exe` from
> `AirGlance_1.0.2.0_x64.msix`, version `0.7.0+c54dbec`). The startup runs used
> an empty settings directory, so they opened at the default fit window
> (1240 × 860); the 100% test used a new directory per run. The package row uses
> the published `v0.7.0` zip. The 0.3.0 figures appear only where this file
> compares the two runs.

| Rendering | Avalonia Win32 software compositor |

The published package includes the optional AVIF decoder, so it is the artifact a
user runs. The startup runs set `AIRGLANCE_SETTINGS_DIR` to an empty directory; an
empty directory opens at the default fit window. Without that, a saved
`zoomMode: actual` from an earlier 100% session turns the "fit window" run into a
full-resolution startup and changes both time and memory.

Test images are generated by `python tools/make-test-images.py`:

| File | Size | Pixels |
| --- | --- | --- |
| `tools/testdata/photo-24mp.jpg` | 0.55 MB | 6000 × 4000 |
| `tools/testdata/photo-100mp.jpg` | 2.1 MB | 10000 × 10000 |

The benchmark images are gradients, so their JPEG files are smaller than photographs of
the same dimensions. The decode work is dominated by pixel count, not compressed size.

## Method

```powershell
$env:AIRGLANCE_SETTINGS_DIR = "<empty settings directory>"
powershell -ExecutionPolicy Bypass -File tools/bench.ps1 -Runs 10
powershell -ExecutionPolicy Bypass -File tools/bench.ps1 -Runs 5 `
  -Image tools/testdata/photo-100mp.jpg
```

Pass `-Exe` to point at the published `AirGlance.exe`. Each run starts a fresh process:

```text
AirGlance.exe --bench=startup <image>
```

The app records elapsed time from the process start time reported by the operating
system to:

- `first_window_ms`: the window's `Opened` event.
- `first_frame_ms`: the first render pass that contains image pixels.
- `decode_ms`: the screen-sized decode, overlap included (the first image is decoded on
  a worker while the window is still being built).
- `peak_ws_mb`: the process peak working set at exit.

`tools/bench.ps1` parses those lines and reports the median and p95. The app has no
console, so the script redirects stdout to a temporary file. A NativeAOT build is the
only comparable build; a normal Release build is a JIT app and is much slower.

### 100 MP JPEG at 100%

Three runs, each with a fresh settings directory so the viewer starts at fit window:

1. Launch the `v0.7.0` `win-x64` AOT build with `tools/testdata/photo-100mp.jpg` alone
   in a folder.
2. Wait for the fit-window preview, press `1`, and sample `WorkingSet64` and
   `PrivateMemorySize64` every 100 ms for 12 s. The tile file is the `*.tiles` file
   under `%TEMP%\AirGlance\tiles`.
3. Record the median of the three runs.

| Point | Working set | Private bytes |
| --- | --- | --- |
| Fit-window preview | 81.4 MB | 49.7 MB |
| Peak, about 0.8–0.9 s after `1` | 464.3 MB | 434.7 MB |
| 2 s after `1` | 125.3 MB | 100.9 MB |
| Peak during the run | 464.3 MB | — |
| Steady state at 100% | 125.3 MB | 100.9 MB |

The 400 MB full decode is unmanaged and is freed as soon as the 512 px tiles are
written; only the visible tile set (32 tiles maximum) stays in memory. The temporary
tile file is about 400 MB while the image is open. The tile file and the peak appeared
in all three runs, so the 100% path was active. The three runs settled at 119.4, 125.3
and 141.4 MB working set; the table uses the median.

The 0.3.0 100% measurement was a single manual run sampled once a second; these are
three runs sampled every 100 ms. At 0.3.0 the same point was 457.6 MB peak and 88.2 MB
steady. The 0.7.0 peak is about 7 MB higher and the steady state about 37 MB higher.
The 0.7.0 package carries the AVIF decoder, which the 0.3.0 package did not; the
fit-window difference is small, and this file does not break the steady-state
difference down further.

## Where the startup time goes

`AIRGLANCE_STARTUP_TRACE=1` prints opt-in marks to stderr. One representative 24 MP run
on the software compositor, with a fresh settings directory:

```text
main=43.3
app-init=74.5
xaml-loaded=79.8
framework-init=117.0
services-ready=125.3
window-ctor-enter=144.5
window-ctor-ui=190.6
window-ctor-vm=191.6
window-ctor-chrome=193.7
window-ctor-exit=194.3
window-created=194.7
window-opened=257.8
image-initialized=266.0
```

The window content now costs about 46 ms (`window-ctor-ui` minus `window-ctor-enter`:
190.6 − 144.5), up from about 14 ms at 0.3.0. The 0.7.0 window builds more chrome — the
dock gained the edit entry and the dual-view controls — while the filmstrip, information
panel and analysis drawer remain lazy. The 24 MP decode (about 58 ms here) overlaps
window construction and image initialisation. This traced run reaches
`image-initialized` at 266.0 ms; tracing adds overhead to the first frame, so the
untraced 24 MP median is the number to use (415.7 ms).

Earlier builds used the ANGLE/GPU compositor. In five 0.7.0 runs with
`AIRGLANCE_GPU_RENDER=1`, the median was 261.9 ms first window and 648.3 ms first frame,
against 250.5 ms and 415.7 ms on the software compositor. Windows therefore keeps the
software compositor by default; `AIRGLANCE_GPU_RENDER=1` switches back.
