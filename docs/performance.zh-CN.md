# 性能

[English](performance.md) · **简体中文**

本文件中的所有数字，都是在下面这台机器上使用所展示的命令测得的。如果某个数字没有出现在这里，说明它没有被测量；本文件中的任何内容都不是推算出来的。

> **版本说明（2026-11-24）：** 下面的计时数据基于 `AirGlance_1.0.2.0_x64.msix` 这个**tag 之后的 Store 包**里的 0.7.0 `win-x64` 二进制，版本 `0.7.0+c54dbec`。该提交比 tag `v0.7.0`（`dca66ab`）晚四个提交，发布工作流从未构建过它，所以它不是 GitHub Release 里的归档；它走的代码路径相同。启动测量使用一个空的设置目录，因此会以默认的适应窗口（1240 × 860）打开；100% 测量每次使用新目录。便携包一行使用已发布的 `v0.7.0` zip。0.3.0 的数字只在本文件做对比时出现。

## 机器与构建

| | |
| --- | --- |
| 操作系统 | Windows 10 Pro 22H2, 10.0.19045 |
| CPU | 2 × Intel Xeon E5-2697 v4，共 16 核 / 16 线程 |
| 内存 | 32 GB |
| .NET SDK | 10.0.403 |
| 运行时 | .NET 10.0.14 |
| 构建 | `packaging/scripts/pack.ps1` NativeAOT `win-x64`，发布在 `AirGlance_1.0.2.0_x64.msix` 中 |
| 渲染 | Avalonia Win32 软件合成器 |
| 日期 | 2026-11-24 |

已发布的包包含可选的 AVIF 解码器，是用户实际运行的产物。启动测量把 `AIRGLANCE_SETTINGS_DIR` 指向一个空目录；空目录会以默认的适应窗口打开。否则，之前 100% 会话保存的 `zoomMode: actual` 会把“适应窗口”测量变成全分辨率启动，时间和内存都会变。

测试图像由 `python tools/make-test-images.py` 生成：

| 文件 | 大小 | 像素 |
| --- | --- | --- |
| `tools/testdata/photo-24mp.jpg` | 0.55 MB | 6000 × 4000 |
| `tools/testdata/photo-100mp.jpg` | 2.1 MB | 10000 × 10000 |

基准测试图像是渐变图，因此其 JPEG 文件比相同尺寸的照片更小。解码工作量主要由像素数量决定，而不是压缩后的大小。

## 方法

```powershell
$env:AIRGLANCE_SETTINGS_DIR = "<空的设置目录>"
powershell -ExecutionPolicy Bypass -File tools/bench.ps1 -Runs 10
powershell -ExecutionPolicy Bypass -File tools/bench.ps1 -Runs 5 `
  -Image tools/testdata/photo-100mp.jpg
```

用 `-Exe` 指向已发布的 `AirGlance.exe`。每次运行都会启动一个全新进程：

```text
AirGlance.exe --bench=startup <image>
```

应用以操作系统报告的进程启动时间为起点，记录到以下时刻为止的经过时间：

- `first_window_ms`：窗口的 `Opened` 事件。
- `first_frame_ms`：首个包含图像像素的渲染通道。
- `decode_ms`：按屏幕尺寸进行的解码，包含重叠部分（第一张图像在工作线程上解码，此时窗口仍在构建中）。
- `peak_ws_mb`：进程退出时的峰值工作集。

`tools/bench.ps1` 解析这些行并报告中位数和 p95。应用没有控制台，因此脚本会把 stdout 重定向到临时文件。只有 NativeAOT 构建才具有可比性；普通的 Release 构建是 JIT 应用，速度慢得多。

## 结果

### 0.7.1，当前口径

24 MP 运行 10 次、100 MP 运行 5 次，使用已发布的 `v0.7.1` Windows x64 构建，取中位数（括号内为 p95）。

| 指标 | 目标 | 24 MP | 100 MP |
| --- | --- | --- | --- |
| 首个窗口 | ≤ 500 ms | **250.7 ms**（550.3） | — |
| 首帧 | ≤ 500 ms / ≤ 2.0 s | **265.9 ms**（575.0） | **309.9 ms**（334.0） |
| 解码 | — | **57.5 ms**（67.4） | **141.0 ms**（147.5） |
| 峰值工作集 | ≤ 250 MB | **63.6 MB**（68.2） | **77.4 MB**（77.7） |

本轮 p95 偏宽，因为测量期间机器同时在跑发布构建与一次 publish；可比的是中位数。100% 缩放的数字见下一节，已为 0.7.1 重新测量。

### 0.7.1，100% 缩放的 100 MP（分块缓存）

三次运行，使用已发布的 `v0.7.1` Windows x64 构建；设置目录预置
`"rememberZoom": true, "zoomMode": "actual"`，启动后每 100 ms 采样一次工作集，持续 18 s，
分块文件大小在同一循环中采样。

| 指标 | 中位数 | 含义 |
| --- | --- | --- |
| 工作集峰值 | **478 MB** | 400 MB 的完整光栅，加上由它构建的位图 |
| 稳定工作集 | **109 MB** | 分块写完、光栅释放之后 |
| 临时分块文件 | **400 MB** | 512 × 512 原始 BGRA，未变 |

`README.md` 里 0.7.0 的 464 MB / 125 MB 是粗读值，不是采样序列。分块文件没有变小，
因为瓦片仍以原始 BGRA 存储——那是下一步的改动，不是这次。

### 100 MP JPEG 在 100% 缩放下

三次运行，每次使用全新的设置目录，保证从适应窗口开始：

1. 启动 `v0.7.0` 的 `win-x64` AOT 构建，并让 `tools/testdata/photo-100mp.jpg` 单独放在一个文件夹中。
2. 等待适应窗口预览，按 `1`，每 100 ms 采样一次 `WorkingSet64` 和 `PrivateMemorySize64`，持续 12 秒。瓦片文件是 `%TEMP%\AirGlance\tiles` 下的 `*.tiles` 文件。
3. 取三次运行的中位数。

| 时点 | 工作集 | 专用字节 |
| --- | --- | --- |
| 适应窗口预览 | 81.4 MB | 49.7 MB |
| 峰值，按下 `1` 后约 0.8–0.9 秒 | 464.3 MB | 434.7 MB |
| 按下 `1` 后 2 秒 | 125.3 MB | 100.9 MB |
| 运行期间的峰值 | 464.3 MB | — |
| 100% 下的稳定状态 | 125.3 MB | 100.9 MB |

400 MB 的完整解码是非托管内存，在 512 px 瓦片写入后立即释放；只有可见瓦片集（最多 32 块瓦片）留在内存中。图像打开期间，临时瓦片文件约为 400 MB。三次运行都出现了瓦片文件和内存峰值，说明 100% 路径确实生效。三次运行的稳态工作集分别为 119.4、125.3 和 141.4 MB；表格取中位数。

0.3.0 的 100% 测量是单次手动运行、每秒采样一次；这里是三次运行、每 100 ms 采样。0.3.0 同一点为峰值 457.6 MB、稳态 88.2 MB。0.7.0 的峰值高约 7 MB，稳态高约 37 MB。0.7.0 的包携带 AVIF 解码器，0.3.0 的包没有；适应窗口的差异很小，本文件没有再进一步拆分稳态差异。

## 启动时间花在哪里

`AIRGLANCE_STARTUP_TRACE=1` 会把需要显式启用的标记打印到 stderr。下面是在软件合成器上、使用全新设置目录的一次有代表性的 24 MP 运行：

```text
main=43.3
app-init=74.5
xaml-loaded=79.8
framework-init=117.0
services-ready=125.3
window-ctor-enter=144.5
window-ctor-ui=190.6
window-ctor-vm=191.6
window-ctor-chrome=193.7
window-ctor-exit=194.3
window-created=194.7
window-opened=257.8
image-initialized=266.0
```

现在窗口内容约耗时 46 ms（`window-ctor-ui` 减去 `window-ctor-enter`：190.6 − 144.5），0.3.0 时约 14 ms。0.7.0 的窗口构建了更多外壳——dock 增加了编辑入口和双画布控件——而胶片条、信息面板和分析抽屉仍然是懒加载。24 MP 解码（这里约 58 ms）与窗口构建和图像初始化重叠。本次追踪运行在 266.0 ms 到达 `image-initialized`；追踪本身会给首帧增加开销，因此应以未追踪的 24 MP 中位数为准（415.7 ms）。

较早的构建使用 ANGLE/GPU 合成器。0.7.0 用 `AIRGLANCE_GPU_RENDER=1` 跑五次，首窗中位数 261.9 ms、首帧 648.3 ms；软件合成器是 250.5 ms 和 415.7 ms。因此 Windows 默认使用软件合成器，`AIRGLANCE_GPU_RENDER=1` 可以切回。
